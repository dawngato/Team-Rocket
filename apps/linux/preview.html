Verification Architecture
How Mathematical Election Verification Works
HimVote replaces administrative trust with 4 independent, mathematically verifiable layers. Every ballot is cast-as-intended, recorded-as-cast, and tallied-as-recorded.
6-Stage Trust Boundary Pipeline
LAYER 01: Student Voter Booth • RFC 9474 Blind Signatures
Zero-Knowledge & Blind Credentials
Voters obtain an RSA blind signature credential from the Identity Issuer. During casting, the booth blinds voter identity completely. The casting server verifies the signature without learning which student submitted the vote.
LAYER 02: Tamper-Evident Merkle Log • RFC 8785 JCS & RFC 9162
Canonical Hashing & RFC 9162 Log
Every accepted ballot is canonicalized per RFC 8785 (JCS) and inserted as an ordered leaf into an append-only RFC 9162 Merkle tree. Any alteration or deletion fundamentally corrupts the tree root.
Institutional Trust Model
Security Guarantees & Cryptographic Limits
In strict compliance with Specification Rule 0.1(7), HimVote never makes unqualified claims such as 'unhackable' or '100% secure'. Below are the exact verified mathematical properties and assumptions.
What Independent Verification Proves
• Cast-as-Intended: The voting booth encrypts the ballot using the election public key before submission.
• Recorded-as-Cast: The Merkle inclusion proof mathematically guarantees the voter's encrypted ballot exists unaltered in the log.
• Tallied-as-Recorded: Universal verifiability allows any auditor to recompute candidate vote counts from the published archive.
• Monotonic Continuity: External witness co-signatures detect if an election database attempts to rewind or erase votes.
